# Security policy

## Supported versions

| Version | Supported |
| --- | --- |
| 0.4.x | Yes |
| 0.3.x and earlier | No (0.4 does not upgrade a 0.3 cluster in place: build it anew) |

## Reporting a vulnerability

Please report vulnerabilities privately through GitHub's private vulnerability reporting: on this repository's
**Security** tab, choose **Report a vulnerability**. Do not open a public issue for them. Include the version
(`coworkerd --version`), how the cluster is deployed (compose or bare metal, the sandbox mode), and the steps to
reproduce. We acknowledge reports and keep you informed until a fix is released.

## Scope and boundaries

- **Tenants and processes.** Tenants share workerd processes, and the boundary between tenants within a process is the
  V8 isolate, as in Cloudflare Workers; workerd itself is not a hardened sandbox. Coworkerd adds per-isolate limits,
  watchdogs and quarantine processes around it ([docs/process-isolation.md](docs/process-isolation.md)).
- **The sandbox.** Each workerd process is started by `coworkerd-launcher` in new mount, network, IPC, UTS and user
  namespaces, as an unprivileged identity with no capabilities and `no_new_privs`; it takes effect only where the host
  allows unprivileged user namespaces, and in the default `auto` mode a node without them runs workerd unsandboxed and
  logs a warning ([docs/guide/install.md](docs/guide/install.md), section 4).
- **The system call allowlist.** The launcher installs an allowlist generated by the build from profiles of the shipped
  workerd binary; it defaults to `observe` (calls outside it are reported and still executed), and only `enforce`
  terminates a process making such a call; the narrower steady-state table is `off` by default.
- **The object store's credentials are the cluster's root.** The cluster's whole state is in one bucket: whoever holds
  the control plane's identity (`deploy`) can change everything the cluster runs. Every node has an identity of its
  own whose prefix policy lets it write only that node's objects (`members/<nodeId>/`, `nodes/<nodeId>/`) and never
  read the credentials index -- a policy of the object store, which compose's `secrets` step writes and an operator
  sets up on bare metal: no daemon refuses a broader identity, and `coworkerd check storage` only reports it; secret
  values are sealed with AES-256-GCM under the cluster's secrets key before they are stored, so reading the bucket
  does not reveal them without that key, which the control plane and every node hold
  ([docs/egress-and-auth.md](docs/egress-and-auth.md)).
- **Trust between components.** The CONNECT that opens each peer connection is signed with a cluster-wide shared key
  when `peerAuth.keyFile` names it (compose always does; without it peer connections are neither signed nor checked,
  and the node warns at startup); the calls inside a connection are not signed one by one, and it is plain TCP, so the
  signature does not detect tampering on the way. The control plane uses admin and tenant credentials, and it and the
  operations tool reach the nodes' management endpoints with the management token, a Bearer header -- a node refuses to
  start without one unless its configuration says `management.allowWithoutToken: true` (development: those endpoints
  are then open, and it warns at startup); there is no mTLS yet, and the object store, the nodes
  and `/v1` are reached over plain HTTP.
