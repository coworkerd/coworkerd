# Egress and authentication

> **Status**: 0.3.0 follows this design except in four points: one etcd tool (`coworkerd-apiserver tool etcd-auth`) sets up users and roles; the administrator credential is generated by the secrets step; the egress tenant is the Worker's tenant; egress bytes are part of the hourly usage.
>
> Premises: [components and boundaries](components.md), [control plane API, first version](control-plane-api.md). Goals: tenant code reaches the network in a controlled way; there is authentication between nodes and between nodes and the back ends; tenant code can never reach the cluster's own ports.

## 1. The starting point

- The tenant Workers' `globalOutbound` is `none`: tenant code **cannot make any outgoing request at all**. Right for test isolation, unacceptable for any platform: applications depend on the network for their databases and third-party APIs.
- Peer calls between nodes (8934) are not authenticated; the management endpoints (`/__coworkerd/` on 8930) have a token; the control plane has credentials; object storage requests are signed and nodes hold only read-only credentials; etcd has no authentication and relies on compose's isolated network.
- Opening the network without the authentication above would let tenant code hit etcd, object storage, the peer port and the control plane directly, so egress and authentication have to land together.

## 2. Where egress lives: a policy point inside the node; the tenant processes themselves still have no network

Each workerd runs in a namespace without network interfaces. Egress does not change that: in the workerd configuration, the tenant Workers' `globalOutbound` points to an external service the node provides, at `<stack>/run/egress.sock` (like the two callback sockets; the launcher already binds `run/` in). Tenant code's `fetch()` reaches this socket through workerd as HTTP, the node connects to the destination on its behalf (including TLS), and sends the answer back. So:

- the sandbox is unchanged, and the tenant processes still have no network; the node is the only way out, hence the only policy point and metering point;
- no change to workerd and no new patch: this is workerd's existing external service mechanism;
- all tenants in a workerd process share one channel, and the node attributes requests to tenants by the origin workerd gives in a request header (the Worker identity attached by the bridge module, in the same way as the nonce in log lines).

## 3. Policy

| Item | Approach |
| --- | --- |
| Destination rules | One set per tenant: allowed and refused hostnames, networks and ports, with cluster-level defaults. **Built-in refusals tenants cannot override**: loopback, link-local, RFC 1918 and ULA private networks, cloud metadata addresses (169.254.169.254 and others), all of the cluster's own addresses and ports (nodes, peers, control plane, etcd, object storage). The platform may let its own internal services through the refusal list; that is the administrator's decision |
| Default policy | Two cluster-level settings: `public` (allow public 80/443, refuse internal) or `deny` (refuse everything; tenants are allowed item by item). The default is `public`, with the platform tightening it in production |
| Name resolution | The node resolves, checks **every** resolved address against the rules, and pins the connection to the checked addresses so that the result cannot change after the check; cached by TTL, with a configurable cap |
| Protocols | HTTP and HTTPS, TLS initiated by the node and verified against the system's root certificates; no long-lived protocols other than WebSocket (later) |
| Limits | A timeout per request; a concurrency limit per tenant; a requests-per-second limit per tenant; the bytes of requests and answers are both metered into the tenant's usage (the egress bytes of `usage`) |
| What a refusal looks like | Tenant code gets a recognizable failure: `fetch` throws an error with `EGRESS_DENIED` and the reason (only the rule's name, no internal details); the node logs an `[egress]` line (tenant, Worker, destination host, result, bytes, duration), counted separately, outside the tenant's log quota |
| Identity | The node adds no identifying headers for the tenant; if the platform needs its internal services to recognize tenants, it uses the tenants' own credentials, not the infrastructure |

## 4. Authentication

| Channel | 0.3.0 | Later |
| --- | --- | --- |
| Peer calls between nodes | A cluster-wide shared key: requests carry a timestamp, a nonce and a signature over the method, the path and the body's hash, with a 30 s window against replays; two keys are accepted at once for rotation; the key is generated by `init` or given in the configuration file, the file 0600 | mTLS and a node join procedure (0.4) |
| Management endpoints | The management token; apiserver uses it to pull logs, state and usage | As above |
| etcd | Turn on etcd's built-in authentication: users and roles as in section 4 of the [control plane API](control-plane-api.md), apiserver reading and writing `/coworkerd/v2/` while only reading `nodes/`, one user per node, writing only its own `nodes/<nodeId>/`; credentials given as files; compose's `init` creates the users and roles, and the bare-metal documentation spells it out | TLS to etcd (0.4) |
| Object storage | Keep signed requests; the deployment credentials only for apiserver, nodes holding only read-only credentials | -- |
| Control plane /v1 | Credentials and scopes | -- |
| Ingress | Tenant traffic is not authenticated anyway; the platform's gateway is in front | -- |

## 5. Unchanged

The sandbox and the launcher; the descriptor conventions between the server and workerd (just one more `run/egress.sock`); placement, the call contract, version locking; the mechanisms of logs and quotas.
