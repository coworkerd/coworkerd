# Egress and authentication

This document is for operators and security reviewers. It describes how tenant code reaches the network -- through one policy point per node, with built-in refusals, pinned resolution, per-tenant rules, limits and metering -- and how the components authenticate each other: the signed peer connection, an object storage identity for every node and one for the control plane, the secrets key, the management token and the `/v1` credentials. The last section lists what is not done yet. The configuration keys and their defaults are in the [installation guide](guide/install.md), section 5, and its sections 11 and 12 describe egress and the cluster key; the errors tenant code sees are in [error codes](guide/errors.md), section 5.

## 1. What has to hold

- Tenant code must never reach the cluster's own services -- object storage, the peer and management ports, the control plane -- whatever address or name it uses.
- Tenant code reaches the rest of the network only through a point that can apply the platform's policy and meter it per tenant.
- Every channel between components has a credential of its own, so being on the cluster's network is not enough to use it -- though the object store may serve more than its S3 interface (section 5). The cluster key is optional, with a startup warning when absent. The management token is required unless `management.allowWithoutToken: true` explicitly opens those endpoints. Compose sets all of this up. The admin credential, the object storage credentials and the secrets key are required: without them the component does not start.

Egress and authentication depend on each other: opening the network to tenants without authenticated back ends would let tenant code talk to them directly.

## 2. The policy point

A tenant isolate's global outbound -- where its `fetch()` goes -- is an entry point of the runtime bridge, bound when the isolate loads to the Worker's full name and version taken from the call, never from tenant code. It forwards the request to the node's egress service on the Unix socket `<stack>/run/egress.sock`, adding a header with its process's egress token; the node opens the connection itself, TLS included, and relays the answer.

- **Attribution.** Every workerd generation has its own random egress token. The node accepts a request only with a live process's token and a valid Worker name, and the tenant is the first part of that name; anything else is refused as `unknown-source`.
- **No identity leaves the node.** The node adds no header of its own and drops its egress headers and the hop-by-hop ones in both directions; a platform service that needs to recognise a tenant uses the tenant's own credentials.
- **No other way out.** With the sandbox active a workerd process has no usable network: its own network namespace has no route and only a loopback device, which is down (a kernel with tunnel drivers loaded adds their inert devices); without it, the only route out for tenant code is still this entry point, because that is how workerd is configured, not because the process could not reach the network.
- `egress.mode` `off` keeps the policy point but refuses every request (`EGRESS_DENIED: egress-off`): an isolate always has an outbound, so a throw after `passThroughOnException` fails that request alone instead of ending the shared workerd process.

## 3. Policy, limits and metering

### Destinations

**Refused whatever a rule says**: the cluster's own addresses on any port; the cloud metadata addresses on the node's list (`169.254.169.254`, `169.254.170.2`, `169.254.169.253`, `100.100.100.200`, `168.63.129.16`, and in IPv6 Amazon's `fd00:ec2::254`, `fd00:ec2::253`, `fd00:ec2::123` and `fd00:ec2::23`, Compute Engine's `fd20:ce::254`, Akamai's `fd00:a9fe:a9fe::1` and Oracle Cloud's `fd00:c1::a9fe:a9fe`); unspecified, loopback and link-local addresses; the reserved ranges on its list -- documentation ranges, multicast and the rest of IPv6 outside the global unicast space among them. An IPv6 metadata address in the unique-local range that is not on the list counts as a private network. An IPv6 form that carries an IPv4 address -- IPv4-mapped, NAT64's well-known prefix `64:ff9b::/96`, 6to4, and the local-use NAT64 prefix `64:ff9b:1::/48` at every place RFC 6052 allows in it -- is judged as that IPv4 address, by every reading when it has several, and each must pass.

**The cluster's own addresses** are every interface address of the node, its listen, peer and advertised addresses, every member's advertised address, the object storage endpoint, the addresses every control plane announces to the nodes (`POST /__coworkerd/control-plane`, every 10 s, forgotten after 10 minutes without an announcement), and `egress.clusterAddresses` -- addresses, CIDRs or names, for the control plane, load balancers and networks a node cannot see by itself. The set is rebuilt every 5 seconds and whenever the membership changes, in the background: the names in it are resolved in parallel, each for at most 2 s, and a tenant's request is checked against the set as it stands, never waiting for a rebuild.

**Private networks** (RFC 1918, 100.64.0.0/10, 198.18.0.0/15, IPv6 ULA and site-local) are refused unless the administrator lists the destination in the tenant's `allowInternal`: the platform's own database or services, a decision tenants cannot make. An address of the local-use NAT64 prefix is judged by the IPv4 addresses it can carry, so an `allowInternal` entry that covers the prefix opens only those that are private ones, never a loopback, metadata, cluster or reserved one; one that carries no IPv4 address at all is reserved.

**The rules**, per address: the tenant's `deny` first; then a private address needs `allowInternal`; a public address passes when `allow` names it -- `allowInternal` opens internal destinations only --; otherwise the default policy decides -- `public` (the default) allows the ports in `egress.publicPorts` (80 and 443), `deny` nothing. An entry is a name, a wildcard name, an address or a CIDR, with an optional port. A name matches a URL that names that host, and a URL that is an IP address through the addresses the name resolves to (a wildcard through the names below it this node resolved within `egress.dnsCacheMs`); an address or a CIDR matches each resolved address both as it is and as the IPv4 address it carries, so a `deny` entry for an IPv4 address also stops that address in its IPv4-mapped, NAT64 or 6to4 form. Rules and limits are per tenant (`egress.tenants[]`, in the node's configuration), shared by all its Workers.

**Resolution and pinning.** The node resolves names itself and checks **every** address of the answer; it connects only to checked addresses, never resolving the name again for the connection. A resolution is reused for at most `egress.dnsCacheMs` (10 s) -- a fixed bound, since the system resolver reports no TTL -- so a name later pointed at a private address is refused at the next resolution. At most 16 resolutions run at once; one whose request's deadline passed holds its place until the resolver answers. The node follows no redirect: tenant code's `fetch` follows each hop as a new request through the policy point, checked again.

**Protocols.** HTTP and HTTPS, each request on a connection of its own, and WebSocket, relayed message by message. The node verifies HTTPS destinations against the system's root certificates (unless `egress.systemTrustStore` is false) and the PEM file `egress.caFile`.

### Limits and metering

- Per tenant and node: `egress.concurrency` requests in flight (32) and `egress.requestsPerSecond` (100, a token bucket); beyond them `EGRESS_DENIED: concurrency-limit` or `rate-limit`, without affecting other tenants. A request counts as in flight until its body or WebSocket session ends.
- `egress.timeoutMs` (30 s) bounds resolution, connecting, TLS and the response headers together, and then each read of either body; WebSocket messages have no timeout.
- The bytes of request and response bodies, and of WebSocket messages, count into the tenant's usage as egress bytes.
- Every request has an `[egress]` line in the node's log -- tenant, Worker, host, port, address, result, rule, status, bytes, duration -- outside the tenant's log; refusals for concurrency and rate are logged at most once per second per tenant, while the counters miss none.
- A refusal is an exception thrown by `fetch`, whose message is the code and the rule or class only (`EGRESS_DENIED: private-network`, `EGRESS_FAILED: dns`), never an address or a name inside the cluster.

## 4. Peer connections: the cluster key

A node calls another over one Cap'n Proto session per peer, opened by an HTTP CONNECT to the peer listener; the node signs that CONNECT with the first key of the cluster key file (`peerAuth.keyFile`): HMAC-SHA256 over the method, the path, the target node's id, a timestamp, a nonce and the body's hash. The calls inside the session are not signed one by one. The listener accepts the session only with a known key, its own id as the target, a timestamp within `peerAuth.windowMs` (30 s) of its clock, a valid signature and a nonce it has not seen; anything else gets 401 and a `[peer-auth]` line with the reason (`unknown-key`, `wrong-target`, `expired`, `replayed` and others). A CONNECT that names another host than `coworkerd-peer` fails before the check.

- **Rotation without interruption.** The file holds one or two keys: the first signs, both are accepted. Adding a key second, making it the first and removing the other -- each step on every node before the next -- changes the key without failing a call, except a call still running, one window after the removal, on a session opened with the old key; compose's `secrets` service has a command for each step.
- **Reloading.** The node checks the file every second and rereads it when it changes; when the new file cannot be read, it keeps the keys it has. A new signing key makes the node open new connections; sessions established with a key that left the file are closed one window later.
- **The file must be private**: a key file with any group or other permission stops the node at its start.
- Clocks of all nodes have to agree within the window (NTP).
- Without a key file, peer connections are not authenticated and the node warns at startup.

The same listener also serves `POST /__coworkerd/trial-load`, `GET /__coworkerd/logs`, `GET /__coworkerd/state` and `POST /__coworkerd/control-plane` (the control plane's announcements of its addresses) over plain HTTP, because the control plane reaches every node at its advertised address for trial loads, logs, state and its announcements. Those requests are not signed: the management token protects them (section 7).

Signing keeps the peer session closed to anything that can reach the port but does not hold the key, tenant code included. It is not mTLS: every node holds the same key, so a node that has it can act as any node.

## 5. Object storage: an identity for every node

The object store holds desired state, code and uploaded durable history; the latest confirmed tail may still be on nodes. Its credentials are the cluster's root: whoever holds the identity the control plane uses can change everything the cluster runs. Every request is signed with AWS Signature Version 4, over plain HTTP, and each component holds only the identity its role needs:

- **`deploy`**, the control plane's and its operations tool's, has the store's `Admin`, `Read`, `Write` and `List` actions on the whole store: it creates the bucket and reads, writes and lists all of it.
- **`node-<nodeId>`**, one for every node, reads the cluster marker, tenant index and manifests, definitions, code, members, `do/` and `nodes/`; lists `members/`, `cluster/tenants/`, `tenants/`, `do/` and `nodes/`; reads, writes and lists its own `members/<nodeId>/` and `nodes/<nodeId>/`; and writes `do/*/shards/*` and `do/*/objects/*`. These new permissions let any eligible node acquire shards, discover alarms, read another owner's log segments, and publish manifests and snapshots after takeover. It cannot read the credentials index or write another node's membership / usage, desired state or code. Durable Object ownership is enforced by conditional epochs and publication fences, not by assigning a storage identity to one shard. A compromised node identity can alter shared object history. Each own-node prefix ends with `/` so `node-1` does not cover `node-10`. [Cluster state](cluster-state.md), section 2, gives the layout.

Compose's `secrets` step generates `deploy` and every node's identity, writes the store's identity file `s3.json`, and gives each service only its own: the control plane and `tool` hold `deploy`, every node its own. `secrets add-node <id>` adds a node's identity while the store runs: the store's container applies it within seconds through `weed shell`'s `s3.configure`, without a restart ([installing and running](guide/install.md), section 2). On bare metal the identities and their policies are the operator's to configure.

`coworkerd check storage` checks a store before use: it creates the bucket, writes a probe object with the deploy identity, reads it back with a node's identity, expects unsigned requests to be refused, checks the contract the cluster relies on, and -- given the node's id in `COWORKERD_READ_NODE_ID` -- reports that identity's policy: its writes below another node's `members/` and `nodes/` and below `cluster/`, and its read of the credentials index, must be refused with `AccessDenied`, while its own prefixes take a write and a removal. The policy is reported, not required: a store that lets a node's identity do more still passes, and the report says so.

What keeps code intact is its hash rather than the identities: every code object a node reads -- a definition, a package, a module, a bundle -- is checked against its hash, so a changed one is refused, never run; the manifests and indexes that name those hashes carry none, and only the identities (the deploy identity alone writes them) keep them intact. Reads are presigned in the query, valid for 60 seconds, signing only the host with an unsigned payload; such a URL names the access key's identifier, though never the secret. In compose only SeaweedFS's S3 gateway listens on the store container's network; its master, volume and filer servers listen on the container's loopback, and the gateway's own gRPC interface trusts a dedicated client certificate authority whose key is discarded and which signs no client certificate. A separate temporary authority signs the gateway's server certificate; its private key remains under `storage/` in the secrets volume, and both authority keys are discarded. The filer serves an identity service of its own without authentication -- on that loopback, so closed: do not publish the filer's ports. `weed shell`'s `s3.configure` prints every identity with its secret, and SeaweedFS writes a full unknown access key into its warnings, so `docker logs` of the store is to be treated as a credential.

## 6. The secrets key

Secrets' values are sealed before they are stored: AES-256-GCM under the cluster's secrets key, a JSON file `{"key":"<64 lowercase hexadecimal digits>"}` readable only by its owner (`secrets.keyFile`, or `COWORKERD_SECRETS_KEY_FILE`). The control plane and its operations tool (`tool secret put`) seal and every node opens; nobody else needs it, and the object store and its identities never see a value in the clear. Each value has a random 96-bit nonce and is bound to `<tenant>/<worker>/<name>`, so a sealed value moved to another secret does not open. A node whose key does not open a value treats the secret as missing: the Worker that declares it is not valid. Compose's `secrets` step generates the key and gives the control plane and every node a copy; state endpoints and logs show only its fingerprint, the first 12 hexadecimal digits of a SHA-256 over the text `coworkerd-secrets-key` followed by the key's 32 bytes. [Control plane API](control-plane-api.md), section 8, describes how values are stored and used.

## 7. The management token and `/v1` credentials

- **The management token** protects everything under `/__coworkerd/` on both listeners of a node except `ready` and `probe`: state, deployment, placement, drain, rotation, trial loads, logs. The control plane sends it to read state and logs, for trial loads and with its address announcements, and the operations tool for trial loads, drains and rotations; nodes do not use it among themselves, their sessions are signed. A request without it gets 401 and a `[management]` line that never contains the token; without a configured token the node refuses startup by default. Only explicit `management.allowWithoutToken: true` opens these endpoints without a token and prints a warning.
- **`/v1` credentials**: the admin credential, configured for the control plane, can do everything; tenant credentials are issued through `/v1`, shown once, stored only as hashes, can expire and be revoked, and act only on their own tenant ([control plane API](control-plane-api.md), section 3). A refused request gets 401 or 403 and a `[control]` line, without the credential.
- **Ingress traffic is not authenticated**: tenants' users reach Workers through the platform's own gateway in front of the nodes.

## 8. Not done yet

- **mTLS between nodes and a procedure for a node to join**: today a node is a member when it holds the cluster key and an object storage identity of its own.
- **Secrets per node**: every node holds the secrets key and opens every tenant's secrets, whatever Workers it runs.
- **TLS to object storage**, between the control plane and the nodes, and for `/v1` itself, which is plain HTTP unless something in front of the control plane terminates TLS.
- **Per-tenant egress rules from the control plane**: the rules are part of each node's configuration.

## 9. RPC trust boundary

Service Binding and Durable Object method calls use workerd's `jsRpcSession()`. The runtime creates the bound target and the trusted envelope (tenant / Worker / version, hashes, tree identity, parent and call sequence, and deadline). The node resolves the tree's pinned versions and allocates the subrequest budget from its own state. Because a JS RPC session carries no `cf`, the shim encodes that envelope in its one method name. The node validates it and routes the session like the corresponding Binding fetch, returning a proxy of the target capability across the peer session when needed.

Application arguments and return values are serialized by the calling isolate and decoded by the target isolate; nodes do not deserialize them as application data. Returned capabilities are held only for the tree's lease. The peer HMAC authenticates the session, not each argument, and all nodes share that key: this boundary trusts the nodes. A tenant controls neither the bound target nor the envelope used to attribute its call. See [compatibility](compatibility.md), section 7, for limits and failure shapes.
