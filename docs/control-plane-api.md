# Control plane API

This document is for platform engineers who integrate with Coworkerd and for contributors to the control plane: the resource model, the `/v1` endpoints, credentials and scopes, quotas and limits and where each is enforced, what uploading, activating, rolling back and deleting mean, routes and hostnames, how secrets are stored, how usage and logs are gathered, and what the version promise is. The error codes are listed in [error codes](guide/errors.md), section 2; the command line that uses this API is in the [quickstart](guide/quickstart.md).

## 1. Resources

One cluster serves one platform, and the platform is its only administrator. Resources have two levels, **tenant -> Worker**; versions, routes and secrets belong to a Worker, and a Worker's full name is `tenant/Worker`.

| Resource | Identifier | Holds | Changed by |
| --- | --- | --- | --- |
| Tenant | 1 to 63 lowercase letters, digits and `-`, starting with a letter or digit, neither `routes` nor `generation`, unique in the cluster | State (`active`, `deleting`), quotas, hostnames, default Worker limits | The administrator |
| Tenant credential | `keyId`, 16 hexadecimal characters | Its scope, one tenant; an optional expiry; whether it is revoked | Created by the administrator; revoked by the administrator, or by the tenant itself |
| Worker | `<tenant>/<worker>`, a name of the same characters and length as a tenant's | Versions, the active version, routes, secrets, the Worker's CPU and memory limits | The tenant and the administrator |
| Version | `<tenant>/<worker>/<version>` | The package in object storage and the definition (compatibility date and flags, variables, Bindings, declared secret names), identified by the definition's hash | Uploaded and deleted, never changed |
| Route | Its host and path prefix | The Worker it points to | The tenant and the administrator |
| Secret | `<tenant>/<worker>/<name>` | A value | The tenant and the administrator |

There is no level above the tenant: a platform that serves other platforms gives each of them tenants of its own. A Worker's Service Bindings may point only to Workers of the same tenant.

## 2. The `/v1` API

Every request carries `Authorization: Bearer <credential>`. Answers are JSON, apart from the log stream (section 10); an error is `{"code","reason"}` with a cleaned reason.

| Method and path | Scope | Purpose |
| --- | --- | --- |
| `GET /v1/status` | Any credential | The answering control plane, the caller, the desired state's revisions, and every node, reduced for tenants |
| `GET /v1/nodes`, `GET /v1/nodes/{node}` | Administrator | Each node's state: processes, sandbox, rotation, suspects, usage |
| `GET /v1/usage` | Administrator | Hourly usage of every tenant |
| `POST /v1/tenants`, `GET /v1/tenants` | Administrator | Create, list tenants |
| `GET /v1/tenants/{t}` | The tenant or the administrator | The tenant's record, its counts and its usage of the last 24 hours |
| `PATCH /v1/tenants/{t}`, `DELETE /v1/tenants/{t}` | Administrator | Change hostnames, quotas and default limits; delete the tenant with everything it owns |
| `POST /v1/tenants/{t}/credentials`, `GET /v1/tenants/{t}/credentials` | Administrator | Issue, list the tenant's credentials |
| `DELETE /v1/tenants/{t}/credentials/{keyId}` | The tenant or the administrator | Revoke a credential |
| `GET /v1/tenants/{t}/usage` | The tenant or the administrator | The tenant's hourly usage |
| `GET /v1/tenants/{t}/workers`, `GET .../workers/{w}` | The tenant or the administrator | The Workers: versions, active version, validity, limits, routes, secret names, Durable Object namespaces |
| `PATCH /v1/tenants/{t}/workers/{w}` | The tenant or the administrator | The Worker's CPU and memory limits, within the tenant's maxima |
| `DELETE /v1/tenants/{t}/workers/{w}` | The tenant or the administrator | Remove the Worker: its active version and routes go, its versions stay |
| `PUT .../workers/{w}/versions/{v}` | The tenant or the administrator | Upload a package and trial-load it; `?activate=true` also makes it active |
| `POST .../workers/{w}/versions/{v}:activate` | The tenant or the administrator | Make an uploaded version active; a rollback is the same |
| `DELETE .../workers/{w}/versions/{v}` | The tenant or the administrator | Delete an inactive version |
| `PUT .../workers/{w}/routes` | The tenant or the administrator | Replace the Worker's routes |
| `GET .../workers/{w}/secrets`, `GET`, `PUT`, `DELETE .../secrets/{name}` | The tenant or the administrator | List names and lengths; show one; set, delete a value |
| `GET .../workers/{w}/logs` | The tenant or the administrator | The Worker's recent log lines from every node, or a stream with `follow` |
| `GET .../workers/{w}/namespaces` | The tenant or the administrator | The Worker's Durable Object namespaces by class: the namespace id, the shards, the status |
| `GET .../workers/{w}/namespaces/{class}` | The tenant or the administrator | One namespace: the owner of each shard an epoch was taken for, and the objects and bytes the nodes report |
| `DELETE .../workers/{w}/namespaces/{class}` | The tenant or the administrator | Mark the namespace deleting, as a version's `deleted_classes` does: no Binding to it and no new request; the data stays |
| `POST /v1/tenants/{t}/databases/{d}`, `GET`, `DELETE` | The tenant or the administrator | Make, show and delete a database (D1's shape): a namespace of its own with one object |
| `GET /v1/tenants/{t}/databases` | The tenant or the administrator | The tenant's databases |
| `POST /v1/tenants/{t}/databases/{d}/query` | The tenant or the administrator | One or more SQL statements on the database, in D1's own request and answer |

Below `/v1/tenants/{t}/`, a tenant that is being deleted accepts only reads: a write is refused with `409 CONFLICT` (`tenant <t> is being deleted`).

**The status answer** names the answering control plane (`apiserver`: its version, its instance and when it started; for the administrator also `storageEndpoint` and `pathRouting`), the caller, the desired state's revisions as this control plane's mirror holds them -- `storage.tenantsRevision` and `storage.credentialsRevision`, with `storage.client`, what its object store client met (requests, retries, timeouts, creates decided by reading back) -- and every member. Two fields of earlier versions stay, always `null`: `etcdRevision`, and the administrator view's `apiserver.etcdEndpoint`. Each member of `/v1/nodes` carries `backend` (`objectStore`) and `lastHeartbeatAgeMs`, how far its heartbeat was behind the store's clock when the members were last listed; every member of `/v1/nodes` and of the status answer, whoever asks, carries `storage.appliedTenantsRevision`, the tenant index revision the node has applied -- what `cowctl deploy`, `rollback` and `secret put` wait for (section 6).

**The control plane keeps no state of its own; it holds a mirror.** At startup it reads the whole desired state from the object store -- the cluster's marker, the tenant index, every manifest the index names and the credentials index -- and refuses to start on a bucket without the marker. Every authentication, and every read of tenants, credentials and secrets' names, is answered from that mirror, so those reads go on while the store cannot be reached, and every write updates the mirror as it commits; a read of a tenant's Workers also needs their version definitions, which the control plane fetches from the store the first time it needs them and keeps -- until then that read answers `503 STORAGE_UNAVAILABLE` while the store cannot be reached. Every `control.pollIntervalMs` (5 s) it reads the two indexes' hints again and reads what another control plane on the same bucket changed. It can be stopped at any time: an interrupted request leaves at most immutable objects, or a committed revision whose hint or tenant index entry is still missing, which the next poll of any control plane on the bucket, or the next start of one, completes -- never a half-written change; an interrupted deletion leaves the tenant `deleting` until it is deleted again (section 6). It is not on the request path: a cluster serves calls while the control plane is down, and only changes wait. The members come from the store too: a listing of `members/` and, once per node and epoch, its heartbeat for the address.

## 3. Credentials and scopes

- **The admin credential** is the platform's own: configured for the control plane (`control.adminCredential`, or `COWORKERD_ADMIN_CREDENTIAL`), 16 to 4096 visible ASCII characters without spaces; compose's `secrets` step generates one. It is not stored in the object store and has no expiry or revocation: changing it means configuring a new one and restarting the control plane. It can do everything and is never given to tenants.
- **Tenant credentials** are issued through `/v1` for one tenant. The text is `cwk_<keyId>_<secret>`, shown only in the answer that creates it; the credentials index `cluster/credentials/<rev>` keeps only the SHA-256 of the secret part. A credential can carry an expiry, can be revoked (the record stays, marked revoked), and acts only on its own tenant.
- Every request checks the credential's record in the mirror, and that its tenant is in the tenant index; secrets are compared in constant time. A credential is created in the credentials index's own turn, after the tenant's latest manifest has been read there: one for a tenant that is being deleted, or that was deleted and created again meanwhile, is refused with `409 CONFLICT`, and a tenant's deletion writes the credentials index's next revision even when it holds none of the tenant's, so a creation that read the index before it is judged again. A revocation takes effect at once on the control plane that wrote it, and on another control plane of the same bucket once it has read the credentials index again (`control.pollIntervalMs`).
- `401 UNAUTHORIZED` answers a missing, malformed, unknown, revoked or expired credential, always with the same reason; only the control plane's log line says which. `403 FORBIDDEN` answers a credential whose scope is not enough: another tenant, or an administrator's endpoint.
- `cowctl` reads a credential only from `COWCTL_TOKEN` or the credential file its `cowctl.json` names (default `~/.cowctl/token`), never from its command line, where other users could see it.

## 4. Writers of the desired state

The control plane writes the desired state -- the tenant index, the tenants' manifests and the credentials index under `cluster/` and `tenants/` in the bucket -- and so does the operations tool (`coworkerd-apiserver tool init`, `apply`, `upsert`, `remove`, `secret`), with the same deploy identity and the same protocol: compose's `init` step runs `tool init` for the marker and the empty indexes -- only `init` creates the marker: the tool's other commands refuse a bucket without it and name the bucket -- and a running control plane sees the tool's writes through its poll. The store's identities keep the nodes out: a node's identity reads the deployment state and the tenants but not the credentials, and writes only its own prefixes. Each change of a tenant is its manifest's next revision, computed from the mirror and created only if absent, so it commits whole or not at all; when another writer created that revision first, the change is read and computed again -- up to 9 attempts for uploads, activations, route changes, Worker removals and secrets, and 8 for the other changes, with jittered pauses -- before it gives up with `409 CONFLICT` and nothing written (the operations tool's `apply` tries once unless `--max-retries` says otherwise) (a secret's write whose failure reason would contain the value -- one of 8 bytes or more -- answers `422 SECRET_REFUSED`, the reason withheld). A change is complete, and answered as done, once it is visible: its revision created, the hint naming it and the tenant index naming it; when the hint or the index cannot be written after the revision was created, the answer is `503 STORAGE_UNAVAILABLE`, the revision stays, and the next write, the next poll or the next start of a control plane completes it (a request repeated meanwhile finds its change made and completes it too). The tenant's record is part of the manifest a change writes, so a write that began before the tenant was marked `deleting` meets the deletion's revision, reads it and is refused. In one control plane the changes of one tenant wait for each other, and changes of different tenants do not, apart from queueing for the tenant index's next revision. The checks that span tenants -- a hostname belongs to one tenant, no route of another tenant is taken over -- are made against the mirror before the write, and the hostnames once more in the tenant index's own turn, where every tenant's entry meets: a tenant's revision that would give it a hostname another tenant's entry holds is refused there with `409 CONFLICT`, and the tenant goes back to the revision the index names (a tenant just created is removed again). The quotas too are checked against one read of the mirror before the write, so concurrent requests can together take a tenant over `workers`, `versionsPerWorker` or `secrets`. The object cleanup of a version's or a tenant's deletion removes an object only when no definition the mirror holds references it and the store's clock says it is older than `control.cleanupGraceMs` (1 hour); a younger one is listed below `cluster/cleanup/` and removed by a later sweep of the control plane if it is still unreferenced. An upload that finds an object present writes it again when it is older than half that grace, and once its manifest is committed checks every object it found and writes a missing one again, so an upload and a cleanup that meet do not leave a definition without its objects. [Cluster state](cluster-state.md) describes the layout, the identities and the write protocol.

## 5. Quotas and limits

| Quota of a tenant | Default | Enforced |
| --- | --- | --- |
| `workers`, `versionsPerWorker` | 100, 50 | By the control plane when a version of a new Worker, or a new version id, is uploaded |
| `packageBytes` | 160 MiB | By the control plane, on the size of the uploaded package, which `control.maxUploadBytes` (also 160 MiB) caps for every tenant |
| `assetFiles`, `assetBytes` | 20,000, 100 MiB | By the control plane on upload |
| `secrets`, `hostnames` | 1,000, 100 | By the control plane when a new secret is set or the hostnames change |
| `logLinesPerSecond`, `logBufferBytes` | 100, 1 MiB | By every node, for the tenant's log lines |
| `maxWorkerCpuMs`, `maxWorkerMemoryMiB` | 30,000, 512 | By the control plane when a Worker's limits or the tenant's default limits are set |
| `durableObjectNamespaces` | 16 | By the control plane when an upload declares a Durable Object class that has no namespace yet, or a database is made (0.5, in development): every namespace of the tenant counts, the databases and those of deleted classes included |
| `durableObjectBytes` | 10737418240 | By the node that owns an object's shard, at the moment a write would be made durable: past it the write answers `422 QUOTA_EXCEEDED` and reads go on. What the tenant holds is what the nodes publish of their own objects (`nodes/<id>/durable-usage`, every `durableObjects.usagePublishMs`), so it bounds the storage rather than accounting for it; the objects of a deleted namespace or database stop counting |

A change over a quota is refused with `422 QUOTA_EXCEEDED` and the quota's name at the start of the reason (`defaultLimits:` for default limits above the maxima), and nothing is written; a package larger than `packageBytes` or `control.maxUploadBytes` -- one of exactly that size is accepted -- is `413 PACKAGE_TOO_LARGE` instead unless the tenant's `packageBytes` is below `control.maxUploadBytes` -- so at the defaults, both 160 MiB, it is 413. The control plane checks these quotas when it admits a change; the log quotas refuse nothing: every node enforces them on the tenant's lines, dropping lines over the rate and the oldest lines over the buffer -- except that a node keeps the tenant's previous values when the buffer quota is larger than its own `logs.totalBufferBytes`. `workers` counts every Worker the tenant's manifest names, a removed one whose versions remain included, and a secret set for a Worker the tenant does not have yet makes one, so it is checked against `workers` too; lowering a maximum leaves Workers' own limits above it as they are, and is refused below the tenant's default limits.

**Worker limits.** A Worker's CPU milliseconds per request and memory MiB per isolate are properties of the Worker (`PATCH .../workers/{w}` with `{"limits":{"cpuMs","memoryMiB"}}`, which replaces both), at most the tenant's maxima. They are stored with the Worker's active version, survive activations and new versions, and go when the Worker is removed. A Worker without its own uses the tenant's default limits, then the node's configuration; nodes apply them per isolate.

**Not limited per tenant**: isolate concurrency and total memory across the cluster, and requests per second at the ingress. Both would need coordination across nodes.

## 6. Versions and deployments

- **Upload** (`PUT .../versions/{v}`): the package is a tar file of a manifest and the version's files. The control plane validates it (format, names, sizes, compatibility date and flags, quotas), stores its modules and assets in object storage by hash, writes the definition `definitions/<hash>` (created only if absent; an existing one must hold the same bytes), and, when the upload activates the version, has a node **trial-load** it in a quarantine process before the tenant's manifest names it: an active version exists only if it loads (one with only static assets has nothing to load and is not tried). A failed trial load answers `422 LOAD_FAILED` with a category; when no node can try, the answer is `503 TRIAL_UNAVAILABLE`.
- **Versions are immutable.** A version id that already has a different definition is refused (`409 VERSION_EXISTS`); uploading the same content again changes nothing. `cowctl deploy` names versions `v1`, `v2`, ... by itself and takes the next number on a conflict.
- **Upload and activate** (`?activate=true`) is checked before anything is published: the Worker must be valid afterwards -- every declared secret has a value, every Binding target is valid and has Worker code, the closure has at most 64 Workers -- and no other valid Worker may become invalid; otherwise `422 DEPLOYMENT_REFUSED`. A failure of the object store is `503 STORAGE_UNAVAILABLE`, told by the failure's kind rather than by the words of its reason, so a refusal whose reason mentions the store is 422 like any other. An upload without it publishes the version without a trial load and checks none of this -- its activation does both (the answer's `record.trial` is `{"enabled":false,"atActivation":true}`) -- and lists no routes: one whose manifest lists routes is refused with `400 INVALID_REQUEST`, since routes are written by an activating upload or `PUT .../routes`.
- **Activate** (`:activate`) moves the active pointer to a version uploaded before and keeps the Worker's routes; it is validated like an activating upload and trial-loads the version again unless it is already active or has only static assets. A rollback is activating an older version.
- **The nodes follow** within a poll interval: each node reads the tenant index's hint every `desiredState.pollIntervalMs` (5 s) and applies what changed, so for up to that long after an answer a node may still serve the previous version, or answer `404 ROUTE_NOT_FOUND` for a new route ([cluster state](cluster-state.md), section 4). Each node reports the tenant index revision it has applied (`storage.appliedTenantsRevision` in `/v1/nodes` and the status answer), and `cowctl deploy`, `rollback` and `secret put` wait until every node that is not draining reports at least the answer's `revision` -- at most 15 s, after which they name the nodes still behind and succeed all the same; `--no-wait` returns at once.
- **Delete a version**: only an inactive one. First the objects in object storage that no other definition of any tenant references go -- modules, then packages and bundles, then the definition, so that a cleanup stopped half way finds the rest again; then the version leaves the manifest. An object younger than `control.cleanupGraceMs` (1 hour, by the store's clock), and every candidate while a remaining definition cannot be read, is not removed but listed for the control plane's sweep (`cluster/cleanup/`), which removes it later if nothing references it then; modules stay, with the packages that list them, when more than 1,000 packages remain or a remaining package's manifest cannot be read, and are listed the same way. When the store cannot be reached or refuses a removal, the answer is `503 STORAGE_UNAVAILABLE` and the version stays in the manifest: deleting it again goes on. Nothing is cleaned when the deleted version's own definition cannot be read. The answer's `objects` counts what was deleted, kept (still referenced) and deferred (`deferredObjects`).
- **Remove a Worker** (`DELETE .../workers/{w}`): its active pointer and routes go and nobody can call it; its versions and secrets stay. It is refused while another valid Worker binds it.
- **Delete a tenant** is a sequence of steps -- the mark, the objects and the credentials are each recorded in the tenant's `deletion` (shown by `GET /v1/tenants/{t}`), leaving the index and removing the manifests are reported in the DELETE's answer (`index`, `manifests`): the tenant is first marked `deleting` in a new manifest revision that keeps its routes and active pointers, so every node refuses new requests to its Workers with `503 TENANT_UNAVAILABLE` and no other tenant takes its routes; then the objects only it uses go -- as for a version, those another tenant still references stay --, then its credentials, then the tenant leaves the index, and finally its manifests and their hint are removed. Calls of trees already running are not refused for the deletion, but can fail once their code is gone. Every step completes or the deletion stops there: a failure after the mark leaves the tenant `deleting` and answers `503 DELETION_INCOMPLETE`, naming the step -- an object the store does not remove, a definition of the tenant that cannot be read, a manifest object left in the last step -- and a mark that cannot be written, or that the tenant index does not name yet, answers `503 STORAGE_UNAVAILABLE`; deleting again goes on from there, every step a no-op where it is already done, until nothing of the tenant remains. Objects the cleanup defers (younger than `control.cleanupGraceMs`, or whose references cannot be read now) are left to the sweep, as for a version. A tenant created again under the name is not kept from the index by a deletion that stopped in its last step.
- **Retention** is the platform's: there is no automatic cleanup of old versions.

## 7. Routes and hostnames

A route maps a host and a path prefix to a Worker. `PUT .../routes` replaces a Worker's routes as a whole (at most 64, a limit only this endpoint checks); an activating upload whose manifest lists routes replaces them too, one that lists none keeps them, and `cowctl deploy` always lists one. A tenant may route:

- **hostnames registered to it** by the administrator; a hostname belongs to one tenant only, and the tenant's list is replaced as a whole when it is changed;
- **paths under the cluster's default host `*`** that are `/<tenant>` or start with `/<tenant>/` -- `cowctl deploy`'s default route is `*` with `/<tenant>/<worker>` -- unless the administrator turns path routing off (`control.pathRouting`): then every route under `*` that a route change or an activating upload lists is refused -- one already written included, so `cowctl deploy` with its default route gets `403 HOSTNAME_NOT_OWNED` --, while the routes already written keep serving.

A request whose hostname is registered to a tenant is matched against that tenant's routes only -- its routes on that hostname and its paths under `*`, the longest prefix covering the path first and, at the same length, the route on the hostname before the path under `*` -- and a path route under `*` serves requests whose hostname belongs to no tenant or to the route's own tenant, never another tenant's hostname ([cluster state](cluster-state.md), section 4). Prefixes match whole path segments, and the control plane writes a tenant's `/<tenant>` under `*` as `/<tenant>/`. Anything else is `403 HOSTNAME_NOT_OWNED`. A route that belongs to another Worker is refused rather than taken over, and a hostname still routed by one of the tenant's Workers cannot be removed from it. Routes are kept in the tenant's manifest with the Worker; how a request finds its route is in [cluster state](cluster-state.md), section 4.

## 8. Secrets

- **Storage.** A secret's value is stored in the Worker's entry of the tenant's manifest, sealed with AES-256-GCM under the cluster's secrets key: a random 96-bit nonce per value, the additional data `<tenant>/<worker>/<name>`, and the ciphertext with its 16-byte tag in base64. The key is a file `{"key":"<64 hexadecimal digits>"}` readable only by its owner, named by `secrets.keyFile` (or `COWORKERD_SECRETS_KEY_FILE`); the control plane seals with it and every node opens with it, and compose's `secrets` step generates it and gives the control plane and every node a copy. Neither the object store nor its identities ever see a value in the clear; state endpoints and logs name the key only by a fingerprint.
- **API.** `PUT .../secrets/{name}` sets the request body as the value; a name is a JavaScript identifier, and a value is at most 5 KiB of UTF-8 without NUL. `DELETE` is refused while it would make a valid Worker invalid. `GET .../secrets` lists names, lengths and when they were set; none of the platform's own answers, log lines or state endpoints shows a value.
- **Use.** A version declares the names it reads, at most 64; a Worker whose active version declares a secret without a value is invalid and not served, and so is one whose value does not open with the node's key -- the node's state names the secret, never its value. Values reach a Worker's `env` when its isolate loads on the executing node, which opens them from its own view of the desired state and hands them to its own workerd process with each dispatch; they never travel with a call to another node. An isolate keeps the values it loaded with until it is replaced.

## 9. Usage

Every node counts, per tenant and UTC hour: requests (each execution of one of the tenant's Workers, Binding calls included), CPU milliseconds, egress bytes, log lines kept and isolate time (resident isolates sampled every second). Every `usage.flushIntervalMs` (one minute) it writes each hour whose counts changed as one object below its own prefix, `nodes/<nodeId>/usage/<hour>`, holding every tenant of that hour, so while the store takes the writes a node that stops loses at most that much (counts whose writes failed stay in memory until a later write takes them; one that cannot read its hour's object at its start counts that hour from zero, and its next write replaces the earlier counts); a draining node writes its last counts before it leaves. Each node removes its own objects older than `usage.retentionHours` (31 days), and the control plane removes every node's at its start and once a day, those of departed nodes included. The usage endpoints list `nodes/` and `members/`, read the objects of the hours in range -- each again only when its ETag changed -- and sum them over whole UTC hours of a range of at most a year -- `?from=&to=` in Unix milliseconds, `to` exclusive, the last 24 hours by default, and `by=hour`, the only grouping; the answer's `nodes` are the nodes named in either listing. So the history does not depend on the control plane. When the store cannot be read, the usage endpoints answer `503 STORAGE_UNAVAILABLE`, and a tenant's `usageLast24h` is `null`.

## 10. Logs

Each node keeps the latest log lines of every tenant in memory, within the tenant's log quota ([process isolation](process-isolation.md), section 10). `GET .../logs` asks every node for the Worker's lines at once, each within `control.serverTimeoutMs` (2 s), and merges them by time -- `since` (Unix milliseconds) and `limit` (1 to 5000, default 200: the newest lines of all nodes together) narrow them; a node that does not answer is listed as unreachable. With `follow`, the answer is a stream of server-sent events (`text/event-stream`) that the control plane fills by asking every node for new lines every 500 ms.

## 11. The version promise

From 0.3.0, `/v1` changes only by adding fields and endpoints until 1.0, and error codes keep their meanings; removing something or changing its meaning goes into a new prefix. A field whose source went away stays, `null`: `etcdRevision` and `apiserver.etcdEndpoint` of the status answer. `ETCD_UNAVAILABLE`, which 0.3 answered on every endpoint while etcd could not be reached, is no longer answered: 0.4 answers most reads from the control plane's mirror, and the writes, the usage endpoints and a read of Workers whose definitions this control plane has not fetched yet (section 2) answer `503 STORAGE_UNAVAILABLE` while the object store cannot be reached.
