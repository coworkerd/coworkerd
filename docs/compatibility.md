# Compatibility with Cloudflare Workers

This document is for platform engineers and contributors who want to know how far Coworkerd runs code written for Cloudflare Workers, and why the line is where it is: how a wrangler project becomes a Coworkerd version, how its code runs, what is checked and refused, and where behaviour differs from Cloudflare's. The [compatibility scope](guide/compat.md) is the checklist for users -- which configuration entries work and which are refused; this document gives the reasons.

## 1. The goal and the line

Coworkerd 0.5 reuses workerd, wrangler and the Workers programming model for stateless Workers, SQLite Durable Objects and D1's basic API. A Worker can accept HTTP and WebSocket requests, call Service Bindings by `fetch` or JS RPC, and call its own Durable Object classes. Objects support SQL, key-value storage, transactions, hibernatable WebSockets and alarms; ownership and recovery are cluster protocols, described in [cluster state](cluster-state.md).

KV, R2, Queues, Workflows, Vectorize and Cloudflare's managed services (AI, Hyperdrive, Email, dispatch namespaces, Access and Rate Limiting) are outside this release. Scheduled triggers and Tail Workers are not dispatched. Durable Object jurisdiction, cross-Worker classes and D1 Sessions are also outside the supported subset.

Anything a project configures outside the line is refused at conversion and listed by name, never ignored silently: an application that silently loses its KV binding is worse than one that does not deploy.

## 2. From a wrangler project to a version

`cowctl deploy` does not bundle code itself:

1. **Check the configuration** against the lists of section 5, before building.
2. **Build with wrangler.** It runs `wrangler deploy --dry-run --outdir` -- the project's own wrangler when one is installed in the project or above it, otherwise the version `cowctl` pins -- and reads the configuration through wrangler's own interface, so TOML, JSON and the configuration a build tool such as the Vite plugin redirects to are read as wrangler reads them. With the pinned wrangler the build runs in a temporary copy of the project, so the output does not depend on where `cowctl` is installed.
3. **Check the asset directory's rule files**, `_redirects` and `_headers`, which the build may produce, after building.
4. **Make a package**: the modules wrangler produced, each with its type, hash and size, and the static assets, in a canonical manifest whose SHA-256 is the package hash. Configuration -- the main module, compatibility date and flags, variables, Bindings, the Durable Object Bindings and classes, the secret names the version reads, the assets settings -- goes into the version definition, not into the package, so the same code can use another configuration with the same content-addressed objects. Every deployment sends its whole package; the control plane creates missing objects, refreshes existing objects older than half the cleanup grace with the same bytes, and repairs missing objects after publishing.
5. **Upload** the package to the control plane as a new version, which validates it, trial-loads it in a node's quarantine process (an ordinary one when the node has none) when it has code, and only then makes it exist and active ([control plane API](control-plane-api.md), section 6); `cowctl deploy --no-activate` uploads without activating, and the trial load comes with the activation.

## 3. How tenant code runs

workerd's dynamic Worker Loader loads a Worker with its own modules, compatibility date and flags and environment, which is what one version needs; the rest is the package format, the deployment state and a bridge module.

- **The runtime bridge** (`runtime/runtime.js`) fetches the version's manifest and modules from its node, checks the package hash and every module's hash, and loads them into an isolate of their own. A bridge module generated per version imports the tenant's main module and dispatches each call to the entry point it names: a class extending `WorkerEntrypoint`, constructed per call, or an object with `fetch`; a named export serves a Binding's `entrypoint`.
- **`env`** holds the version's variables and secrets, fixed when the isolate loads, and the call's Bindings, which change from call to call because they carry the call tree's identity and budget; they arrive through `ctx.props`. The bridge runs the handler inside `withEnv`, so `import { env } from "cloudflare:workers"` sees the same `env` during a call; at a module's top level it sees the variables and secrets.
- **A Binding is a capability bound to its target.** Tenant code gets a stub created by the platform for one target Worker and version; it cannot name another target, and the node executes exactly the target the definition approved.
- **A Durable Object** is an object of one of the version's classes, named by its namespace's id and its own. The control plane makes a class's namespace id when a version first declares the class and keeps it for the class's name in later versions. Every call to an object goes to the node's durable process (`d0`), where the runtime keeps an object of its own, `Host`, for each one: the Host runs the tenant's class as its facet, from the isolate the Worker Loader keeps for the version under the same key as the version's stateless calls -- with the same CPU and memory limits -- and with a SQLite database of its own. A namespace Binding in `env` has `idFromName`, `newUniqueId`, `idFromString`, `get` and `getByName`; a stub has `fetch`, a WebSocket upgrade included.
- **Compatibility flags** are the version's own plus `enable_request_signal`, which the platform always turns on because cancellation depends on `Request.signal`; `disable_request_signal` is refused. It also adds `rpc` unless the version already specifies `rpc` or `no_rpc`.

## 4. What is checked at deployment

| Item | Rule | Why |
| --- | --- | --- |
| Compatibility date | A real date, not later than the maximum of the bundled workerd | Later dates name behaviour this runtime does not have |
| Compatibility flags | On the allowed list generated from the bundled workerd's sources (both names of every non-experimental flag, 294 in all) | Experimental features stay off |
| Modules | Safe names (no `..`, not absolute, not starting with `__coworkerd_`), a supported type (ES module, CommonJS, text, data, JSON, WebAssembly), a main module that is an ES or CommonJS module; at most 10 MiB together, uncompressed | The bridge and the cache address modules by name and hash; counting uncompressed is simple and predictable |
| Variables | At most 64, JavaScript identifiers, each at most 5 KiB, plain text or JSON | Names, types and sizes are checked at deployment |
| Secret names | At most 64 per version, JavaScript identifiers, none shared with a variable or Binding | Secrets, variables and Bindings share one `env` |
| Static assets | At most 20,000 files, 25 MiB each, 100 MiB in total: defaults that `COWORKERD_ASSET_MAX_COUNT`, `COWORKERD_ASSET_MAX_FILE_BYTES` and `COWORKERD_ASSET_MAX_TOTAL_BYTES` change for the adapter, the control plane and the nodes alike; the tenant's `assetFiles` and `assetBytes` quotas apply as well, and wrangler's asset manifest, which the adapter builds first over the asset directory (with the project's own wrangler, `.git` and the local value files included; the adapter's own wrangler builds from a copy without them), refuses a file over 25 MiB or more than 100,000 files whatever they say | As on Cloudflare per file; the total is conservative |
| Loading | The version is trial-loaded: imports, top-level code, the entry point's export, the CPU and memory limits while loading | A deployment is a rare, watched moment, the cheapest place to find a load error |
| Durable Objects and durability | SQLite classes of this Worker, 1024 shards per class namespace, one owner per shard. Objects run in durable processes; peers confirm frames before responses (local flush with an empty selected peer list), and segment / snapshot recovery preserves uploaded history and the surviving peer tail. Simultaneous loss of owner and all confirming peers can lose the unuploaded tail; 30 s is the normal segment interval, not a loss bound during an outage. `DO_RECOVERING`, `STORAGE_UNAVAILABLE`, object-size and tenant-quota failures are explicit. The object env contains variables, secrets, DO and D1 bindings, without Service Bindings; clone and jurisdiction are refused, location hints ignored. | [Durable Object guide](guide/durable-objects.md), [cluster state](cluster-state.md), sections 11–12 |

The flags' list and the maximum date are generated from the workerd sources the patch series applies to (`scripts/compatibility-flags.py`, into `common/generated/`, which is committed): following upstream means running it again by hand, since no build step runs it.

## 5. Configuration entries

- **Mapped**: `name`, `main`, `compatibility_date`, `compatibility_flags`, `vars`, `services` (Service Bindings, with `entrypoint`), `assets`, `durable_objects` (Bindings to the Worker's own classes: `name` and `class_name`, a `script_name` only when it names the Worker itself) and `migrations` (in their order: `new_sqlite_classes` and `new_classes` both declare a SQLite class, `renamed_classes` moves a class's namespace to its new name, `deleted_classes` marks it deleted; `tag` is accepted), and the build entries wrangler uses to produce the modules; `$schema` and `send_metrics` are accepted and change nothing. Source maps are not kept: the adapter drops wrangler's `.map` output, whatever `upload_source_maps` says.
- **Accepted, ignored, reported**: `observability`, `placement`, `workers_dev`, `preview_urls`, entries with empty values, and, in a configuration a build tool redirected, wrangler's own path and name fields (`configPath`, `userConfigPath`, `topLevelName`) and fields equal to their defaults. The first four are Cloudflare's own logging, scheduling and URL settings and change nothing the code does -- refusing them would leave almost no real project convertible --, and the others carry no configuration of the Worker; all are listed in the conversion's output as ignored.
- **Refused**: stateful and cloud bindings other than Durable Objects and `d1_databases`, a Durable Object class of another Worker (a `script_name` naming another Worker, `transferred_classes`), `triggers`, wrangler's own `secrets` entry, `routes`, `route` and `env` -- routes in Coworkerd are the platform's: hostnames the administrator registers to a tenant, or `/<tenant>/...` under the cluster's default host -- `_redirects` and `_headers` with rules, a non-default `assets.html_handling`, and any key not on the lists.
- **Secrets**: a version declares the names it reads -- those of the project's `.dev.vars.example` and the `--secret NAME` arguments of that deployment; values are set separately with `cowctl secret put`. The adapter takes no values from `.dev.vars` or `.env`, and the pinned wrangler builds in a copy of the project that leaves them out, with an empty `--env-file`. A project's own wrangler builds in the project directory: there a wrangler too old for `--env-file`, or a build command of the project's own, can still read them. Whichever wrangler builds, they are never published as static assets: the adapter leaves `.git` and the files `.dev.vars`, `.dev.vars.*`, `.env` and `.env.*` (other than `*.example`) out of the assets.

## 6. Static assets

Assets are part of the package: each file with its path, hash, size and content type, stored by hash like modules, so unchanged files share the same object keys and a version's assets change only with its package hash. Uploads can refresh old existing objects with the same bytes and repair missing ones after publication. The adapter lists them as `wrangler dev` does, with the same ignore rules and content types, and in addition leaves out `.git` and the local value files `.dev.vars`, `.dev.vars.*`, `.env` and `.env.*` (`*.example` excepted).

The node serves them itself, without workerd or placement -- and, for a request at the ingress, without a lease -- in the order Cloudflare's asset routing uses: for `GET` and `HEAD`, the exact path, `index.html` for a path ending in `/`, `<path>.html` and `<path>/index.html` for the rest; where Cloudflare would redirect to an equivalent URL, the file is served directly. A hit gets `ETag` (the content hash) and, when the request has neither `Authorization` nor `Range`, `Cache-Control: public, max-age=0, must-revalidate`; a matching `If-None-Match` gets 304. A miss goes to the Worker; a site without a Worker, or a configuration that asks for it, falls back by `not_found_handling` (`none`, `404-page`, `single-page-application`). Methods other than `GET` and `HEAD` on paths the asset layer answers get 405. A browser navigation request (`Sec-Fetch-Mode: navigate`) falls back to the asset layer under the same compatibility flags as on Cloudflare (`assets_navigation_prefers_asset_serving`, `assets_navigation_has_no_effect`).

`assets.binding` gives the Worker an `ASSETS` Binding whose `fetch()` is answered by this version's assets; it starts no child call, so it does not draw on the subrequest budget. `run_worker_first` -- `true`, or path patterns with `!` exclusions -- sends matching requests to the Worker first. A Service Binding call to a Worker with assets goes through its asset layer too, unless it names an entry point, and is charged to the budget like any Binding call.

## 7. Differences from Cloudflare

| Item | Coworkerd | Why |
| --- | --- | --- |
| `request.cf` | Coworkerd's call metadata: `nodeId`, `workerId` as `tenant/Worker`, `versionId`, `invocationId` and others, 13 fields; `serverId`, the field's earlier name, is a deprecated alias of `nodeId` (the same value), removed in 1.0; no geography or TLS data | There is no source for that data inside a cluster |
| `request.url` | Always `http://`, with the host and without its port; the client's headers pass unchanged, and the node adds no client address of its own | The node's ingress rebuilds the request |
| Inbound WebSocket | Supported for stateless Workers: a Worker answers an upgrade with `101` and a WebSocket, and the node that received the upgrade relays text and binary messages and close frames (code and reason) both ways -- also when the Worker runs on another node, through the peer session, which the connection keeps for its life. Each message runs with the request's CPU and memory limits and renews the call tree's lease, its deadline and its budget of subrequests: a message's Service Binding calls and theirs share the root's budget (four calls by default). Over a limit the connection closes with `1011` and the code an HTTP answer would carry. A message is at most 32 MiB, there is no idle timeout and no compression; a draining node and a process being replaced close their connections with `1001`; a node holds at most `ingress.webSocketsPerTenant` (1000) open connections of one tenant (`429 WEBSOCKET_LIMIT` beyond them). The lines its handlers write reach `cowctl logs` as each message runs, within 256 KiB a message. A Durable Object accepts connections the same way, with hibernation (below) | A connection is one request, and its messages are the request's events |
| `ctx.props` | The platform's (`bindings`, `entrypoint`, and `durableObjects` when present); tenants cannot pass props through a Binding | Bindings carry the call tree's identity and budget |
| Service Bindings | Only to Workers of the same tenant, by `fetch` and by JS RPC: `env.SVC.method(args)` on the default entry point or on a named one (`entrypoint`), with Cloudflare's serializable types -- structured clone, `RpcTarget`, `RpcStub`, streams, functions -- and the exception the method throws reaching the caller as it does on Cloudflare. A method call is a call of the tree like a `fetch` through the Binding: it draws on the budget of subrequests, carries the deadline, and is placed like any call, so the target may run on another node (the node proxies the capability over the peer session; the arguments are serialized in the calling isolate and decoded in the target's, never in between). A method of a class the Worker does not export as a `WorkerEntrypoint` is refused: a plain object entry point has `fetch` only. Calls on a capability a method returned are part of the same call and draw nothing further | RPC between isolates is workerd's own; what a cluster adds is where the target runs |
| Durable Objects and durability | SQLite classes of this Worker, 1024 shards per class namespace, one owner per shard. Objects run in durable processes; peers confirm frames before responses (local flush with an empty selected peer list), and segment / snapshot recovery preserves uploaded history and the surviving peer tail. Simultaneous loss of owner and all confirming peers can lose the unuploaded tail; 30 s is the normal segment interval, not a loss bound during an outage. `DO_RECOVERING`, `STORAGE_UNAVAILABLE`, object-size and tenant-quota failures are explicit. The object env contains variables, secrets, DO and D1 bindings, without Service Bindings; clone and jurisdiction are refused, location hints ignored. | [Durable Object guide](guide/durable-objects.md), [cluster state](cluster-state.md), sections 11–12 |
| Hibernation and alarms | Hibernatable connections survive idle object-tree eviction, and their next message wakes the object. The resident target is 4096 trees per durable process, `0` unlimited; active trees may exceed it. A process or node exit closes connections. Alarm time is durable database state; per-object hints discover due objects after takeover. A missing hint can delay delivery until the object reopens; handlers must tolerate retries. | The connection relay survives object eviction, not a failed node; hints are not authoritative |
| D1 | One namespace, shard and platform SQL Worker object per database. `prepare`, `bind`, `first`, `all`, `raw`, `run`, `batch`, `exec`, the CLI and HTTP SQL are available. `batch` executes statements in order without an encompassing transaction; `exec` splits lines. The default object cap is 10 GiB; no Sessions, dump, migration / import / export tool, replicas or point-in-time restore. `database_id` is ignored; `database_name` selects within the tenant. | The database has the same confirmation, recovery and quota semantics as an object |
| Durable Object ids | 64 hexadecimal digits, as on Cloudflare but derived otherwise: `idFromName` is the SHA-256 of the namespace id, `name` and the name; `newUniqueId` is 32 random bytes; `idFromString` takes any 64 lowercase hexadecimal digits, so an id carries no proof of its namespace, while `get` refuses an id object another namespace made | Objects are kept apart by the namespace id the platform adds to each, whatever id a Worker presents |
| Durable Object failures | An exception the class throws leaves the object as it is, as on Cloudflare: the same instance takes the next request, and the caller's `fetch()` answers `500 EXECUTION_FAILED` with the exception's message (`error`, `code`, `reason`) where Cloudflare's throws it. A request over a limit resets the object: `503` with `CPU_LIMIT_EXCEEDED` or `MEMORY_LIMIT_EXCEEDED`, and the next request constructs the class again, its data intact. The limit ends the version's isolate in the durable process, so every object of that version there -- of any of its classes -- starts again at its next request | A version's objects share one isolate on a node, and a limit is enforced on the isolate |
| Calls between Durable Objects | An object's call to an object -- by `fetch` or by a method -- starts a call tree of its own, with its own deadline, and is not charged to a budget; a chain of more than 8 such calls is refused (`508 DO_HOP_LIMIT`). A stateless Worker's call to an object is a Binding call of its tree, charged to its budget | An object serves the call trees of many callers and its own calls belong to none of them; the hop limit bounds a chain |
| Capabilities over RPC | A `RpcTarget`, an `RpcStub`, a stream or a function that crosses a Binding is a capability of the call tree that made it: it can cross this node and the peer session within that call, remains subject to workerd's restriction against using I/O capabilities in a later request, and is released with the tree's lease -- a call on it after the lease has run out answers `LEASE_EXPIRED`, and one whose node has gone answers a disconnection. The arguments and the return value of one call are at most 32 MiB serialized, workerd's own limit; a larger value fails the call | A capability reaches across machines only while something is there to carry it |
| Load failures | Refused at deployment by the trial load. At run time, before a version's first call in a process and again once its last check there is older than `placement.idleMs` (30 s), a load check refuses the call before it executes: `LOAD_FAILED` -- a missing entry point included --, `LEASE_EXPIRED` when the check runs out of time, `RESULT_UNCERTAIN` when the process dies during the check (`LOAD_FAILED`, `limit`, when the check was its culprit). The check confirms the version in a process, not one isolate, so a new isolate can load between checks without one (for example after an early eviction, after a call hit a limit, or after the Worker's limits changed); a load that fails then fails inside the dispatched call: `RESULT_UNCERTAIN`, or `CPU_LIMIT_EXCEEDED` / `MEMORY_LIMIT_EXCEEDED` when a limit ended it; `loadCheck` can turn the check off | A refusal before the code ran tells the caller that nothing executed |
| Failures after dispatch | Before the response started, `RESULT_UNCERTAIN`, or `CPU_LIMIT_EXCEEDED` / `MEMORY_LIMIT_EXCEEDED` when a limit ended the call; after it started, the response is cut | Part of the code may have run |
| `passThroughOnException` | After a throw, workerd sends the request on to the Worker's outbound, which is the node's egress service: it goes to the request's own URL like an outgoing `fetch`, and a refusal there answers `500`; with egress off the policy point refuses it (`EGRESS_DENIED: egress-off`) and the request fails on its own | Falls back to the origin |
| `ctx.waitUntil` | Work after the response completes; its Binding calls are refused once the call tree's deadline has passed (`LEASE_EXPIRED`) | The lease covers the call tree, not the work that follows it |
| Limits | CPU 200 ms per request and memory 128 MiB per isolate by default, adjustable per Worker within the tenant's quota | The CPU limit is also the bound of what one request can add to its neighbours' latency |
| Assets | No `html_handling` redirects (content is served directly), no compression, no `Range`, the route's prefix is not stripped from asset paths | Kept simple; the content is the same |
| Logs | `cowctl logs` from each node's per-tenant buffer, with quotas per tenant; lines arrive as they are written, at most 256 KiB an event -- a request, or a message of a WebSocket connection; an object's events are its requests and its connections' messages together --, past which the event's lines are cut, with one warning line in their place | No Workers Logs or Tail Workers |

## 8. How compatibility is checked

The stateless compatibility baseline deployed real projects without changing their code, through the wrangler adapter `cowctl` uses, and compared their answers with `wrangler dev` (local workerd) for the same requests; The pre-0.5 template baseline converted Cloudflare's official templates: 3 of 41 convert with their configuration unchanged, and 11 in all when the templates' own build runs first; the others fail on entries this document lists as refused -- stateful and cloud services most of all -- or on their own build, not on the converter. The release package's `examples/` holds two of them as they are, `email-routing-template` (static assets and the `ASSETS` Binding) and `x402-proxy-template` (a secret).

**Known 0.5.0 limitations:** acknowledged object writes can be lost after an abrupt same-disk restart. A D1-only Worker without a declared DO class has no D1 binding in its env. See [Durable Objects](guide/durable-objects.md) and [databases](guide/databases.md) for the reproduced limits and HTTP SQL retry behavior.
